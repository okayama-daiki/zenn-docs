## はじめに

クエリの種類に応じて実装すべきロジックが変わる場面はよくあります。
Web API やバッチ処理、イベント処理などでは、同じ入口から入りつつも、実際にはまったく異なる責務の処理を行うことになります。
本エントリでは、このようなケースに対して段階的にリファクタリングを行い、どのタイミングでどのような設計を行うべきかについて整理します。

入力としては、コーディングテストでもお馴染みの標準入力から 1 行ずつ文字列で与えられるケースを想定します。

```txt
query_type_1 param1 param2
query_type_2 param1 param2
query_type_1 param1 param2
query_type_3 param1 param2
...
```

これらを適切な方法でパースして、オブジェクトのリスト `queries` に変換したとします。

```python
class QueryType1: ...
class QueryType2: ...
class QueryType3: ...

queries = [
    QueryType1(param1, param2),
    QueryType2(param1, param2),
    QueryType1(param1, param2),
    QueryType3(param1, param2),
    ...
]
```

## Stage0: 条件分岐による実装

既に各クエリが適切にパースされているとして、まずはナイーブに if 文や switch 文で条件分岐を行う実装です。

```python
for query in queries:
    if isinstance(query, QueryType1):
        # query_type_1 の処理
    elif isinstance(query, QueryType2):
        # query_type_2 の処理
    elif isinstance(query, QueryType3):
        # query_type_3 の処理
```

書き捨てのコードか、もしくはクエリの種類が限られており、今後も増える見込みがないのであればきっとこれで十分なのでしょう。さもなければ次のような悪夢を見ることになるかもしれません。

```python
for query in queries:
    if isinstance(query, QueryType1):
        # query_type_1 の処理
    elif isinstance(query, QueryType2):
        # query_type_2 の処理
    elif isinstance(query, QueryType3):
        # query_type_3 の処理
    elif isinstance(query, QueryType4):
        # query_type_4 の処理
    elif isinstance(query, QueryType5):
        # query_type_5 の処理
    ...
    elif isinstance(query, QueryTypeN):
        # query_type_N の処理
```

新しいクエリの種類が増えるたびに条件分岐を追加するのは面倒ですし、あまり触りたくないですよね。このような実装では、クエリの追加と同時にこの分岐自体を修正する必要があり、変更の影響範囲が分かりにくくなります。match/case 文が使える言語であれば多少はマシになるかもしれませんが、根本的な解決にはなりません。
では、この問題に対してどのような改善が考えられるでしょうか。

## Stage0.5: ストラテジーパターンによる実装

オブジェクト指向プログラミングによる解決法は、各クエリ（データ）に対して処理も一緒に持たせる方法です。

```python
class QueryType1:
    def handle(self):
        # query_type_1 の処理
class QueryType2:
    def handle(self):
        # query_type_2 の処理
class QueryType3:
    def handle(self):
        # query_type_3 の処理

for query in queries:
    query.handle()
```

この方法では、クエリの種類ごとに処理が分散されるため、条件分岐が不要になります。
新しいクエリを追加する際には、新しいクラスを定義し、その中に処理を実装すればよいだけです。

しかしながら現実世界のシステムでは、クエリの処理は往々にして外部リソースに依存していたり複雑なビジネスロジックを含んでいたりします。
ただし、この方法ではクエリのデータと処理が強く結びついてしまい、関心の分離が難しくなる場合があります。
また、関数型プログラミングを主に採用しているプロジェクトでは馴染みにくいかもしれません。

## Stage1: 関数マッピングによる実装

クエリの種類ごとに処理を関数として切り出し、クエリとその関数をマッピングする方法を考えてみましょう。
条件分岐を排除し、対応関係をデータとして表現する発想です。
関数が第一級オブジェクトとして扱える言語であれば、およそ以下のように実装できます。

```python
def handle_query_type_1(query):
    # query_type_1 の処理
def handle_query_type_2(query):
    # query_type_2 の処理
def handle_query_type_3(query):
    # query_type_3 の処理
query_handlers = {
    QueryType1: handle_query_type_1,
    QueryType2: handle_query_type_2,
    QueryType3: handle_query_type_3,
}

for query in queries:
    query_handlers.get(type(query))(query)
```

今後新しいクエリに対応する時には、新しい関数を定義し、マッピングに追加するだけで済みます。
`for` ループ内は一切変更する必要がなく、影響範囲が限定されます。

しかしこの方法でも、関数が増えるたびにマッピングの定義を修正する必要があります。

## Stage2: 関数デコレータによる実装

この問題を解決するために、多くの言語がサポートしているデコレータ構文が利用できます。

```python
query_handlers = {}
def register_query_handler(query_class):
    def decorator(func):
        query_handlers[type(query_class)] = func
        return func
    return decorator

@register_query_handler(QueryType1)
def handle_query_type_1(query):
    # query_type_1 の処理
@register_query_handler(QueryType2)
def handle_query_type_2(query):
    # query_type_2 の処理
@register_query_handler(QueryType3)
def handle_query_type_3(query):
    # query_type_3 の処理

for query in queries:
    query_handlers.get(type(query))(query)
```

これにより、クエリの種類ごとに関数を定義するだけで自動的にマッピングに登録されるようになりました。
既視感を覚えた方もいらっしゃるかもしれませんが、これは flask や fastapi などの Web フレームワークでルーティングを定義する方法と非常に似ています。

Python であれば、`functools.singledispatch` よりエレガントな方法もあります。

```python
from functools import singledispatch

@singledispatch
def handle_query(query):
    ...

@handle_query.register
def handle_query_type_1(query: QueryType1):
    # query_type_1 の処理
@handle_query.register
def handle_query_type_2(query: QueryType2):
    # query_type_2 の処理
@handle_query.register
def handle_query_type_3(query: QueryType3):
    # query_type_3 の処理

for query in queries:
    handle_query(query)
```

自分でマッピングを管理する必要がなくなりました。簡単ですね。
